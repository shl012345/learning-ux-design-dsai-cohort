# CONTENT-SPEC.md

The contract every `.md` file in `/content` must satisfy. The build script reads this shape. Deviating from it breaks the build.

This file is also the contract for forks of this template. If you're adapting the repo for your own topic, read [`FORK.md`](./FORK.md) first, then come back here for the field-by-field reference.

## Four kinds of file

| Kind | Where it lives | Purpose |
|---|---|---|
| **Site config** | `/site.config.json` | Site-level metadata. One per repo. |
| **Section metadata** | `/content/<...>/_section.md` | One per section folder. Defines the section's title, summary, and order. |
| **Lesson** | `/content/<...>/<NN>-<slug>.md` | The actual learning content. As many per section as needed. |
| **Example artifact** | `/examples/<filename>` | Real source code that lessons reference and excerpt. See [`/examples/README.md`](./examples/README.md). |

The build script (`lib/content.ts`, generated by Antigravity) walks `/content/` at build time. It treats every subfolder as a section and every `.md` file as content. Section folders are discovered, not enumerated. There is no central list to maintain.

Files in `/examples/` are read on demand when a lesson references them via `real_world_excerpt` frontmatter or an inline `<RealWorldCallout />` component.

## Lesson frontmatter

Every lesson `.md` file starts with YAML frontmatter:

```yaml
---
title: "What design actually is"
section: "foundations"
order: 1
duration: "20 min"
difficulty: "beginner"
prerequisites: []
analogy: "Building a house vs. picking the paint"
tags: ["mindset", "fundamentals"]
summary: "One-sentence summary used on the section index page."
---
```

### Field reference

| Field | Type | Required | Notes |
|---|---|---|---|
| `title` | string | yes | Display title |
| `section` | string | yes | Must match a section slug. That's the folder name, which also matches the `_section.md` slug. |
| `order` | number | yes | Sort order within the section, 1-indexed |
| `duration` | string | yes | Approximate read-and-do time, e.g. `"20 min"` |
| `difficulty` | string | yes | One of `beginner`, `intermediate`, `advanced` |
| `prerequisites` | string[] | yes | Array of prior lesson slugs (filename without `.md`). Use `[]` for the first lesson. |
| `analogy` | string | yes | The signature analogy used in the lesson |
| `tags` | string[] | yes | Short tag strings for filtering and search |
| `summary` | string | yes | One-sentence summary used on section index pages and meta description |
| `real_world_excerpt` | object | no | A primary "see this in real code" callout, rendered as a sidebar. See below. |

### Optional `real_world_excerpt` field

Lessons can anchor a concept in a real artifact by pointing at a file in `/examples/` and a line range. The artifact is typically a snippet of production code, a config file, a JSON design-token export, or a small annotated transcript. Anything that benefits from being shown in context rather than retyped into prose.

```yaml
real_world_excerpt:
  source: "<short human-readable name of your artifact>"
  file: "examples/<your-file>"
  lines: "12-24"
  caption: "What this excerpt illustrates, in one sentence."
  sees_in_depth: "<section-slug>/<lesson-slug>"
```

| Sub-field | Type | Required | Notes |
|---|---|---|---|
| `source` | string | yes | Human-readable name of the source artifact |
| `file` | string | yes | Path relative to the repo root, e.g. `examples/<your-file>` |
| `lines` | string | yes | Line range as `"start-end"`, 1-indexed, both bounds inclusive |
| `caption` | string | yes | Short explanatory caption shown alongside the excerpt |
| `sees_in_depth` | string | no | Slug of a later lesson that dissects this excerpt fully |

The build script reads the file at build time, slices the lines, syntax-highlights, and renders the result as a sidebar callout on the lesson page. It does not copy the lines into the markdown. The file in `/examples/` is the single source of truth.

> If your topic has no anchor artifact, this field is optional. Every lesson can omit it. The `RealWorldCallout` component still gets generated; it just goes unused.

### Inline real-world callouts

For additional excerpts mid-lesson (beyond the primary one in frontmatter), use the inline component in MDX:

```mdx
<RealWorldCallout
  file="examples/<your-file>"
  lines="20-22"
  caption="What this excerpt illustrates."
/>
```

Multiple inline callouts per lesson are fine. The component is generated by Antigravity during scaffolding.

## Section metadata (`_section.md`)

Every section folder under `/content/` must contain a `_section.md` file. It carries the section's metadata and a short description. The leading underscore keeps it sorted to the top and signals "this is not a lesson".

```yaml
---
slug: "foundations"
title: "Foundations"
order: 1
summary: "Mindset, classes, objects, and the self parameter."
duration: "~90 min total"
icon: "📚"
---

A short paragraph or two describing the section. Renders on the section index page as the section's intro.
```

### Field reference

| Field | Type | Required | Notes |
|---|---|---|---|
| `slug` | string | yes | Must match the folder name exactly |
| `title` | string | yes | Display title for the section |
| `order` | number | yes | Sort order across sections, 1-indexed |
| `summary` | string | yes | One-line summary used on the home page |
| `duration` | string | no | Approximate total time across the section's lessons |
| `icon` | string | no | An emoji or icon identifier. Decorative only. |

The body of `_section.md` (everything after the closing `---`) renders as the section index page's introduction.

## Site config (`site.config.json`)

Single source of truth for site-level metadata. See the file itself for the full shape. It has inline `_comment` keys explaining each section. The fields you'll edit most often when forking:

- `site.title`, `site.tagline`, `site.description`, `site.url`
- `author.name`, `author.email`
- `navigation.primary` and `navigation.secondary` — section slugs in display order
- `branding.accentColor`, `branding.fontHeading`, `branding.fontBody`
- `features.*` — feature flags
- `footer.copyright`

The `navigation.primary` and `navigation.secondary` arrays must contain section slugs that exist as folders under `/content/`. A slug listed but with no folder, or a folder not listed in either array, produces a build warning.

## Body conventions

- Use `##` for top-level sections, `###` for subsections. Never `#`. The title comes from frontmatter.
- Use fenced code blocks with language tags: ` ```python `
- Use `>` blockquotes for instructor commentary or asides
- Keep paragraphs short (3–5 sentences). Online reading rewards brevity.
- One concept per section. Don't combine.

## Slugs

The lesson slug is the filename without the `.md` extension. Example: `01-what-design-is.md` produces the slug `01-what-design-is`. The numeric prefix sorts the file in directory listings and matches the `order` field.

The section slug is the folder name. It must match the `slug` field in `_section.md`.

## Adding a new field

When adding a new frontmatter field:

1. Update this spec with the field name, type, and meaning.
2. Update the build script (`lib/content.ts`) to handle it.
3. Backfill all existing files, or make the field optional with a sensible default.

## Removing a field

Don't, unless you also update every existing `.md` file in the same commit. Optional fields are forgiving. Required fields are not.

---

## Validation

The build runs a frontmatter validator (`scripts/validate-content.ts`, generated by Antigravity). It confirms:

- Every `.md` file under `/content/` has frontmatter
- Every required field is present
- Every `section` field references a real section folder
- Every `prerequisites` entry references a real lesson slug
- No two lessons in the same section share the same `order`

Validation runs on every push via Vercel's build step. A broken file fails the deploy rather than shipping silently.
